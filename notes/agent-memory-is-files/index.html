An agent's memory is the files it writes

Published on 14 November 2026.

The fourth task in one chain asked about the user's Messages conversations. The agent read them from the Chats app instead, a different messaging app in the same environment. It saved what it found to two files in its home directory, convs.json and names.json, and answered wrong. Four tasks later, another question about Messages conversations. The agent made no app call at all: it opened convs.json and answered wrong again. Four tasks after that, the same thing happened a third time.

Two copies of the same agent, one starting each task with no memory and one carrying only the conversation, queried Messages each time and got all three right.

The bug itself is small. It shows something about how this kind of agent remembers: its memory is the files it writes to disk, and the conversation adds little. This note is about a small experiment that separates the two.

Sequential Gaia2

Gaia2 is Meta's benchmark for agents that act in a simulated phone: contacts, email, calendar, messaging apps, cab rides, apartment listings. Each scenario is a user request, and a judge checks the agent's actions and answer against an oracle. Normally each scenario starts from scratch.

Sequential Gaia2, added in September, chains the scenarios of one universe (one simulated user) together. The agent does 11 to 20 tasks in a row, and each task starts with what the previous one left: the agent's home directory, its conversation session, and the state of the apps. That is closer to a personal assistant that works for the same person every day. The agent here is OpenClaw, the harness Meta uses for its own Gaia2 numbers. It has a shell, can write files, and compacts its conversation when the context fills up.

"Carries memory" covers two different things: the conversation, and the files the agent chose to write. I wanted to know which one does the work.

The experiment

What the next task starts with
A full carryconversation + files the agent wrote (the default)
B conversation onlyconversation; files the agent wrote are deleted
C no carrynothing: each task runs on its own (standard Gaia2)

B needed a 17-line switch in the runner: after each task, keep OpenClaw's own state and persona files, and delete everything else the agent wrote to its home. I ran the three conditions on all 10 chains of the search split, 160 tasks each, with deepseek-flash as the agent's model. Search tasks only read data, so the right answer never depends on what an earlier task did.

Memory does not make the agent more accurate. The three conditions pass about the same number of tasks. On one chain run three times per condition, the pass counts move by one between runs, as much as between conditions.

It makes the agent do less work, and all of that comes from the files. In the second half of a chain, with files carried, the agent needs a median of 5 app calls per task, against 19 when it starts fresh. With only the conversation carried it needs 25, no better than starting fresh.

The conversation costs more than it gives. B reads 28% more input tokens per task than C and saves no calls. A long conversation is expensive to carry, and after compaction it holds little the agent can use.

What the agent's memory looks like

Reading the traces explains the numbers. Early in a chain, the agent often writes a short Python script that pages through a whole app and dumps it to a JSON file: contacts.json, inbox.json, events.json, rides.json. Later tasks answer by running Python over those files instead of calling the apps. When the conversation gets compacted, the summary does not keep the data, only where it is. In one run the summary said, in effect, "Dumped all 125 contacts to /home/agent/contacts_raw.txt".

So the memory that matters is a small file-system cache plus a pointer to it in the conversation summary. Take away the files and the pointer leads nowhere. The agent has to query the apps again, while still paying for the long conversation.

Nobody told the agent to build this cache. It decides on its own, and the decision varies:

  • On one chain it dumped emails, calendar and chats, and needed a median of 2 app calls per task in the second half.
  • On another it saved only contacts, apartment listings and crime statistics, and needed 80, more than both other conditions.

On 8 chains of 10, full carry needs fewer calls than starting fresh. How much less depends on what the agent happened to save.

When the cache is wrong

Back to the opening example. In that chain the cache was wrong from the moment it was written: it held Chats data under a generic name. Nothing in convs.json says which app it came from, which query produced it, or when. A later task asking about Messages finds a file called convs.json, and nothing tells the agent not to trust it. One early mistake turned into three wrong answers. The agents without the cache made it zero times.

This is one chain and three tasks, so I count it as a case and not a rate. It happened on the read-only split, where the data never changes. On tasks that write to the apps, a cache that was correct when written can also go stale. Sequential Gaia2 orders those chains on purpose so that earlier writes do not break later oracles, so that case is not measured yet. It is the next thing I want to test.

For anyone building agents that keep files across sessions: the agent's own notes are a cache. A cache needs a record of where each entry came from, a way to be invalidated, and some check against the source. Here the agent kept none of these.

Limits

  • One model, one harness, the search split only.
  • One run per condition on 9 of the 10 chains. Differences of a few passed tasks are within noise.
  • The judge is the same model as the agent.

Bugs found along the way

The runs also turned up two ways the evaluation can misreport a result. I opened these on the Gaia2 repository:

  • When the judge's own LLM call fails, the scenario is counted as a FAIL. Replaying 147 passing trajectories with a broken judge, 41 (28%) flip to FAIL. PR #130 reports them as errors instead. PR #129 makes the judge temperature configurable.
  • When the agent's model provider fails (billing, timeout, unknown model), the error text is sent to the user as the answer and graded as a wrong answer (issue #131).
